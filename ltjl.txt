## 一、这个仓库/站点的关键背景信息（继续操作前必读）

### 1. 部署方式：push 即部署，不需要手动 build
- 站点接了 **Vercel** 的 GitHub 集成，push 到 `main` 分支后 Vercel 会自动拉代码、跑 `hexo generate`、部署上线，全程自动化，**不需要**手动 `hexo clean && hexo g` 再部署。
- `.github/workflows/indexnow.yml` 是配套的 GitHub Action：push 后等待90秒（等Vercel部署生效），再跑一次 `hexo generate`，目的是触发 hexo 的 IndexNow 插件提交更新链接给搜索引擎，**不负责部署**。
- 本地这台VPS **没有安装 `node_modules`**，且系统 Node 版本是 v18.20.4，而项目用的 `hexo@8.1.2` 要求 Node ≥20.19，本地跑 `hexo generate` 大概率会因为版本不匹配出问题。真要本地验证构建，需要先升级 Node（用 nvm）。日常不需要这么做，改完 push 就行。

### 2. Git 推送凭据与身份
- 这台VPS一开始没有配置 GitHub 推送凭据。解决方式：`apt-get install -y gh`，然后 `gh auth login --hostname github.com --git-protocol https --web`（用 `run_in_background` 方式跑，避免设备码过期），用户用手机浏览器打开链接输入验证码授权，之后 `gh auth setup-git` 让普通 `git push` 生效。**这个授权状态应该会保留在这台机器上**，继续操作前先 `gh auth status` 确认还在，不用重新走一遍这个流程。
- 提交作者身份统一用仓库历史里已有的 `ziyouhua <freedomdengyong@outlook.com>`（本地 `git config`，不是全局），不要用其他身份。

### 3. ⚠️ 重要坑：用户手机 Termux 里还有一个独立的 clone
用户会用手机 Termux 连接**另一台机器/环境**，那边 `~/myhexo` 是这个仓库的**另一个独立clone**，跟这台VPS的 `/root/myhexo` 不是同一个工作目录。本次会话中已经真实发生过一次混乱：用户在 Termux 里执行了命令，误以为是在这台VPS上执行，导致两边 git 历史一度分叉（Termux那边提交了一个无关的 `session-summary-2026-09-12.md` 文件，用的还是命令示例里的占位符提交信息"你的提交信息"）。

**继续操作时的原则**：不要假设用户描述的"我执行了xxx命令"就是在你所在的这个环境里执行的。如果用户报告的命令结果和你自己 `git log`/`git status` 看到的对不上，大概率是在别处执行的，先用 `git fetch` + `git log` 核实，不要凭空猜测或强行"修复"看似正常的状态。

### 4. URL/permalink 规则
- `permalink: :year/:month/:day/:title/`，即文章URL由**发布日期**（`date:` 字段）和**文件名**（不含扩展名）组成，`abbrlink` 字段虽然存在于部分文章的front matter里，但**没有实际启用**，不影响URL。
- **写内部链接前，务必用 `curl -s -o /dev/null -w "%{http_code}" <url>` 实测一下目标URL是否返回200，不要凭猜测的日期/文件名拼URL**——这次修复的多个404都是因为链接时日期猜错了（差1-2天，或者差了一整年）。

### 5. 一个隐藏的日期陷阱：`date: 2026-08-28 24:00:00` 这种非法时间
`24:00:00` 不是合法时间，Hexo会把它进位成第二天的 `00:00:00` 来生成实际URL，但如果front matter和文件内嵌的JSON-LD结构化数据（`datePublished`/`dateModified`/`url`字段）里的日期没有跟着更新，就会导致**文章自己的结构化数据描述的URL跟真实URL对不上**。这次全站排查发现两处（`iconic-one-download.md`、`3x-ui-shadowsocks.md`），已修复为合法时间（次日00:00:00），永久排除了整个仓库中这种写法。**以后新建文章如果日期字段手滑写成 `24:00:00` 这类非法值，记得用同样的方法排查修复。**

### 6. Markdown渲染器的"自动识别域名"陷阱
Hexo的Markdown渲染器会把看起来像域名的裸文本（比如 `acme.sh`、`tcpx.sh` 这种"单词.tld"格式）自动转成超链接（linkify行为）。如果这类文本紧贴着中文字符没有空格分隔（比如"底层调用的是acme.sh"），渲染器可能把相邻的中文字符也一起当成域名的一部分，编码成一个乱码的IDN域名（比如 `xn--acme-z49g32ji6rdg3artci61f.sh`，反解码后正是"底层调用的是acme.sh"），导致这个不存在的域名出现在页面里，被链接检测工具报告为 "host not found"。**以后正文里提到工具名/脚本名这种"看起来像域名"的裸文本（`xxx.sh`、`xxx.com`这种），一律用反引号包起来（``` `acme.sh` ```），既符合行内代码的语义，也从根本上阻止渲染器误判。**

### 6. sitemap治理 + tag合并（应对GSC"100+网页已发现-尚未编入索引"）
用户反馈GSC提示100多个网页"已发现-尚未编入索引"，排查出两个根因，均有具体数据支撑：

1. **内容发布速度过快**：全站154篇文章，光8-9月两个月就发了89篇（占58%），一个只有16个月历史、权重有限的站短期内容量暴增，Google给的抓取配额跟不上，导致大量新页面积压在"已发现未抓取"状态。**这一条没有代码能修，只能等，且建议近期不要进一步加快发文速度**，让配额消化掉积压。
2. **Tag严重泛滥**：144个不同tag对应154篇文章，其中**121个tag只被1篇文章用过（占84%）**，每个tag都会生成一个独立的、内容跟对应文章高度重复的薄内容归档页。sitemap里146个tag页比154篇文章本身还多，严重稀释抓取配额。

处理措施（commit `c5d915f`）：
- `_config.yml` 的 `sitemap:` 配置加了 `tags: false`，sitemap从311条URL降到约165条，不再主动把这146个tag页推给Google抓取（页面本身没删，只是不再通过sitemap索取）。
- 合并了27组明显是同义词/拼写变体的孤儿tag到已有的常用tag（比如"IPv6 only VPS"等4个变体全部并入"IPv6"，"BBR/BBR原理/BBR3"并入"BBR加速"，"S-UI面板搭建"等5个并入"S-UI教程"），tag总数144→117，单篇孤儿tag数121→95。

## 三、给继续操作的AI工具/人的建议

1. **做任何"内链数量"相关的改动前，记住用户的明确态度**：内链宁少勿多，宁可只做"子文章链回主篇"这种轻量、自然的单点补充，不要搞成每篇文章互相交叉链接的复杂网络。加链接优先考虑"是否自然、是否真的对读者有用"，而不是单纯为了SEO堆链接。
2. **任何"新写一篇文章去抢某个关键词排名"的提议，先用WebSearch查一下实际竞争格局，但结果要请用户自己上Google核实**（工具查的排序不可靠，教训见上文第三节）。中文VPS/科学上网这个圈子，NodeSeek、NodeLoc这类论坛权重极强，很多话题小站基本抢不过，判断值不值得写之前先摸底。
3. **写任何内部链接前，先curl验证目标URL返回200**，不要凭猜测的日期/路径直接写。
4. **正文里提到看起来像域名的裸露英文短语（尤其是`xxx.sh`这类），记得包反引号**，避免被Markdown渲染器误判成超链接。
5. **改动完成后，标准收尾动作是 `git add -A && git commit -m "..." && git push origin main`**，push后Vercel自动构建部署，不需要额外操作。commit message 请照着这次会话里的风格写：一行标题概括改了什么，空一行后用几句话说清楚背景/根因/处理方式，方便以后回看。
6. 前面提到的4个还没决定的tag合并方案（SSH相关、WordPress相关），可以主动跟用户确认后执行，不要自己臆断合并规则。
